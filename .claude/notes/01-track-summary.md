# Конспект ТЗ: трек «Образовательные решения» (хакатон, MAX)

Источник: `internal/Образовательные решения.pdf` (22 стр.), сырой текст — `internal/track_raw.txt`.

## Суть
Чат-бот (или чат-бот + мини-приложение) на Платформе для бизнеса в MAX, решающий **конкретную, обоснованную** проблему в образовании. Токен бота выдают организаторы.

## Этапы
- **Онлайн (MVP):** ЦА и сегмент → проблема + подтверждение → UX основного сценария → MVP в MAX → масштабирование → ожидаемый эффект и метрики → презентация, отбор в финал.
- **Офлайн-финал:** 29 октября, Казань. Пилотный сценарий, доработка, защита. 3 призёра на направление.

## Контекст / цифры (для обоснования)
- 2026/27: >38 тыс. школ, 18 млн школьников; ~4 млн студентов в 3,2 тыс. колледжей (Минпросвещения 2026).
- >17,7 млн детей в кружках/секциях (Минпросвещения 2025).
- Единая модель профориентации 2025/26: >8,5 млн школьников, >14 тыс. предприятий, >36 тыс. школ, ~3 тыс. колледжей, 900 вузов.
- «Сферум»: ~35 млн пользователей, 2,5 млн педагогов (2024/25), интегрирован с MAX.
- VK Education: 37 вузов-партнёров, 135 программ в 2025, 310 тыс. участников.
- Боль: информация в разных системах, условия зависят от региона/возраста/статуса, процессы требуют нескольких организаций.

## Направления-подсказки (не ограничивают)
1. Доп. образование и возможности развития (кружки, секции, проекты, наставники).
2. Карьера и стажировки (практика, стажировки, первая работа, связь с рынком труда).
3. Обратная связь и управленческая аналитика (сбор/анализ фидбэка, повторяющиеся проблемы).
4. Безопасность, психологическая поддержка, инклюзия (передача специалисту обязательна).

## Ограничения (жёсткие)
- Тематика трека + обоснованная актуальность.
- MAX — среда реализации; основной сценарий проверяется в MAX, работает и в мобильной, и в веб-версии.
- Форма: чат-бот ИЛИ чат-бот + мини-приложение (мини-апп не изолирован от бота).
- Свой API не обязателен и баллов не даёт.
- Рекомендуют JS/React, но можно другое.
- Моковые данные вместо реальных интеграций — явно указывать.
- Нельзя: закрытые библиотеки, частные API, чужой код без свободной лицензии; секреты в репо.
- Ник бота нельзя сменить после создания.
- После дедлайна код не меняется (фиксируется commit hash).

## Рекомендации организаторов
1. Узкая ЦА (возраст, уровень, роль, регион, ситуация).
2. Подтвердить проблему (статистика, открытые данные, интервью, аргументированные допущения; факты ≠ гипотезы).
3. Один приоритетный сценарий end-to-end.
4. Сначала задача, потом технология. «Создадим AI-ассистента / навигатор / агрегатор» — анти-паттерн как стартовая формулировка. Чувствительные кейсы — эскалация человеку.
5. Данные: ПДн несовершеннолетних, 152-ФЗ, обезличенные/тестовые данные, кто видит что.
6. Масштабирование = перенос в другой контекст: ядро vs переменная часть.

## Формат сдачи (обязательно)
1. Работающий бот/мини-апп в MAX (ссылка).
2. Git + commit hash.
3. README.md: назначение, сценарий, архитектура, **одна команда Docker**, env, порты, зависимости, внешние сервисы, данные, тестовые данные, пошаговая проверка, ожидаемое поведение, ограничения, остановка/перезапуск.
4. Lock-файл зависимостей.
5. Dockerfile, compose.yaml, .dockerignore, .env.example; сборка ≤ 5 мин.
6. PDF-презентация: слайд 1 — техинфо (ссылки, hash, тестовые логины, **рабочие токены/ключи**, порядок сценария; не оценивается). Далее: название/команда, executive summary, ЦА/проблема, решение/сценарий, эффект, архитектура, данные/интеграции, масштабирование, риски/допущения, источники.
- Если есть свой API: HTTPS-адрес, OpenAPI 3.x, тест-учётки, тест-данные, DATA-API.yaml. → **Проще без собственного публичного API.**

## Критерии (шкала 0–3)
**Допуск (иначе 0):** по теме и в MAX; бот запускается и сценарий проверяем; есть презентация.

**Онлайн-этап** = 40% продукт + 60% техника.
- Продукт: масштабирование 35%, польз. ценность 25%, UX/UI 20%, целостность 15%, презентация 5%.
- Техника: работоспособность 30%, интеграция/данные 20%, стабильность/ошибки 20%, архитектура 10%, безопасность/зависимости 10%, документация 10%.
- **Платформенный бонус +0,15** (всё или ничего): возможность MAX сверх минимума, с пользовательской ценностью, работает end-to-end, описана. (Кандидаты: мини-приложение, MAX Bridge — геолокация/контакты/шаринг/QR/хаптика и т.п., MAX UI, уведомления, диплинки — сверить с актуальной докой.)

**Финал** = 40% техническая оценка + 60% защита.
- Защита: ценность 25%, масштабирование 25%, качество MVP/UX 20%, пилот/внедрение 15%, защита/ответы 10%, командное владение 5%.

### Выводы по весам
- Масштабирование — самый тяжёлый продуктовый критерий (35% онлайн, 25% финал) → идея должна иметь чёткое «ядро + переменная часть» и понятный путь тиражирования (регион → регион, школа → колледж и т.п.).
- Техника 60% онлайна, из них 50% — «сценарий проходится + не падает» → узкий, надёжный MVP важнее фич.
- UX: состояния загрузки/результата/ошибки, без тупиков.
- Пилот нужен уже к финалу: первый регион/организация, владелец процесса, каналы, метрики.

## Подсказки MAX
- Бот API, конструкторы, MAX Bridge (API MAX + устройства, платформа запуска), MAX UI (React-компоненты). Мини-апп только по HTTPS.
- Чат — для: последовательные вопросы, выбор из немногих опций, персональный результат, проверка статуса, уведомления/напоминания, регулярные короткие действия.
- Мини-апп — для: сложные формы, много параметров, сравнение, списки/каталоги, возврат к данным, сложный визуал.
- Сверяться с актуальной докой и changelog API MAX.

## Где искать проблему (чек-лист из ТЗ)
- инфа размазана по источникам; ручное сопоставление программ/требований; порядок действий зависит от региона/возраста/статуса; непонятно, что подходит и какой следующий шаг; много участников (ученик/педагог/организация/работодатель); ручной перенос данных специалистами; отслеживание сроков/статусов; разрывы между сервисами и повторный ввод; обращения «просто чтобы понять, что делать».
- Шаблон: **[Пользователь] в ситуации [контекст] хочет [результат], но сталкивается с [барьером], из-за чего [последствие].**
- Процесс: As Is → To Be → гипотеза «Если мы поможем X сделать Y с помощью Z, то R станет лучше, потому что…» + метрика → границы MVP (MoSCoW, особенно Won't).

## Данные
Первоисточник; дата/территория актуальности видна пользователю; разделять факт / расчёт / рекомендацию / допущение; не имитировать интеграции; LLM — привязка к источникам, фолбэк «не знаю».
