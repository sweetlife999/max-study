# Кампус — онбординг первокурсника и отметка в MAX

Онбординг первокурсника, активности и отметка по ротирующему QR — мини-приложение и чат-бот
в мессенджере MAX.

Работающий бот: [`t200_hakaton_max_bot`](https://max.ru/t200_hakaton_max_bot). Мини-приложение можно
открыть [прямой ссылкой](https://max.ru/t200_hakaton_max_bot?startapp) или кнопкой в диалоге с ботом.
Публичный стенд и API: `https://max.fblrkus.ru`.

**Контракт проекта — [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).** Он меняется отдельным PR;
реализация обязана ему соответствовать.

Данные в демо синтетические и не являются данными реального вуза или студентов. Продукт не
привязан к конкретному вузу: всё вузовское — в
[`config/university.example.yaml`](config/university.example.yaml).

## Основной пользовательский сценарий

1. Студент открывает бота в MAX, нажимает «Начать» и «Открыть приложение».
2. При первом входе студент принимает согласие. Приложение показывает онбординг и ближайшие
   активности; ручные шаги можно отметить сразу, событийные закрываются после посещения.
3. Студент выбирает событие и подтверждает участие. Ожидаемый результат — статус «Вы идёте».
4. Организатор переходит в раздел управления, создаёт текущее событие и включает отметку.
5. Экран организатора показывает ротирующий QR и шестизначный код. Студент сканирует QR камерой
   MAX или вводит эти шесть цифр в разделе «Отметка».
6. После успешной отметки студент видит начисленные баллы и выполненный шаг онбординга, а
   организатор — участника в посещаемости и CSV-выгрузке.

Роль организатора выдаётся одноразовой ссылкой: владелец бота передаёт её проверяющему через
защищённый канал, проверяющий открывает ссылку, нажимает «Начать» и повторно запускает
мини-приложение. Ссылку нельзя коммитить: она даёт повышенные права и действует один раз.

## Быстрый старт

```sh
cp .env.example .env  # секретов в репозитории нет, .env в .gitignore
# Впишите в .env настоящий MAX_BOT_TOKEN и имя бота в MAX_BOT_USERNAME.
docker compose up --build
```

Эта команда поднимает PostgreSQL, применяет миграции, идемпотентно загружает демо-данные,
запускает API, бота и Caddy с мини-приложением. Мини-приложение доступно на
`http://localhost:8080`; запросы к `/api` Caddy отправляет сервису `api` внутри Compose-сети.
Сам `api` также слушает `http://localhost:8000` (порт меняется через `API_PORT`), проверить его
можно командой `curl http://localhost:8000/health`. При первом запуске найдите в логах `seed`
приглашение организатора. Остановка стека: `docker compose down`.

`api` и `bot` без `MAX_BOT_TOKEN` в `.env` не стартуют и будут перезапускаться — это
намеренно: бот без токена не может опрашивать MAX, а api не может проверить подпись
`initData` ни одного запроса (§7). Токен выдаёт @MasterBot; впишите его в `.env` до запуска.

## Backend локально

Нужен [uv](https://docs.astral.sh/uv/) и Python 3.12.

```sh
cd backend
uv sync
uv run ruff check && uv run ruff format --check
uv run pyright
uv run pytest --cov=campus --cov-report=term-missing
```

Процессы запускаются теми же командами, что и в контейнере: `uv run python -m campus.api`
(FastAPI на порту 8000) и `uv run python -m campus.bot` (long polling, нужен `MAX_BOT_TOKEN`).

Контракт для фронта пересобирается из приложения; CI падает, если файл устарел:

```sh
cd backend
uv run python -m campus.api.openapi ../docs/openapi.json            # перегенерировать
uv run python -m campus.api.openapi ../docs/openapi.json --check    # проверить, как в CI
```

Интеграционные тесты работают на настоящем PostgreSQL: либо укажите `TEST_DATABASE_URL`, либо
оставьте его пустым — тогда testcontainers поднимет базу сам (нужен Docker). Живых вызовов MAX
тесты не делают: клиент подменяется на `campus.max.fake`.

Миграции:

```sh
cd backend
uv run alembic upgrade head        # DATABASE_URL из окружения
uv run alembic check               # модели не должны расходиться с миграциями
```

## Web локально

```sh
cd web
npm install
npm run api:types:check
npm run lint && npm run typecheck && npm run test && npm run build
```

После изменения `docs/openapi.json` обновите сгенерированные типы командой
`npm run api:types`.

Production-like образ мини-приложения собирается из каталога `web/` и запускается через Caddy:

```sh
docker build -t campus-web:local web
```

Для запуска внутри MAX одного публичного HTTPS недостаточно: владелец бота должен открыть
платформу MAX для партнёров → Чат-боты → бот → ⋮ → Настройки и в разделе «Мини-приложение»
сохранить адрес `https://max.fblrkus.ru` (или свой `PUBLIC_WEB_URL`) и выбрать кнопку запуска.
После этого проверьте кнопку «Открыть приложение» в чате и ссылку
`https://max.ru/t200_hakaton_max_bot?startapp`. Поле `web_app` у inline-кнопки содержит имя
бота, а не HTTPS-адрес сайта. [Инструкция MAX](https://dev.max.ru/docs/webapps/introduction).

Полный список — §10 контракта и комментарии в [`.env.example`](.env.example). Токен бота нужен

## Состав и интеграции

```text
MAX mobile/web ── MAX Bridge/initData ──> Caddy/React
       │                                      │
       └──── Bot API <── Python bot           └── /api ──> FastAPI ──> PostgreSQL
```

- Caddy раздаёт React SPA и проксирует `/api/*`, `/health` и `/openapi.json` в FastAPI.
- FastAPI проверяет подписанный `X-Max-Init-Data`, хранит пользователей, события и посещаемость.
- Отдельный процесс бота получает обновления MAX long polling и отправляет сообщения через Bot API.
- MAX Bridge предоставляет данные запуска, кнопку назад, камеру QR и системный share UI.
- PostgreSQL — единственное постоянное локальное хранилище; миграции выполняет Alembic.

## Возможности MAX в продукте

Сверх минимального «бот + мини-приложение» продукт использует возможности платформы там, где они
убирают шаги из основного сценария:

| Возможность | Где в сценарии | Зачем пользователю |
|---|---|---|
| Камера MAX (`openCodeReader`, без выбора файла из галереи) | «Отметка» у студента | Скан QR на месте без сторонних приложений; фото из галереи не принимается |
| Диплинк `?startapp=ci_<событие>_<код>` внутри QR | Скан системной камерой | QR открывает мини-приложение сразу на подтверждении отметки |
| Подписанное время скана из `initData` | Проверка кода на сервере | Задержка сети не «сжигает» код, отсканированный вовремя |
| Ротирующая картинка QR в чате организатора (`POST /uploads` + `PUT /messages`) | «Отправить QR в чат» | Организатор показывает QR с телефона прямо из диалога с ботом |
| Максимальная яркость экрана | Экран QR организатора | QR читается в светлом зале; яркость возвращается при выходе |
| Уведомления и напоминания бота (`outbox`) | После RSVP и отметки | Напоминание о событии, подтверждение отметки и закрытого шага онбординга |
| Системный share UI (`shareContent` / `shareMaxContent`) | Приглашение организатора | Администратор пересылает одноразовую ссылку в нужный чат MAX |
| Тактильный отклик, кнопка «Назад», закрытие мини-приложения | Результат отметки, навигация | Понятная обратная связь и возврат в чат после отправки QR |

Локально используются порты `8080` (mini-app), `8000` (прямой API) и `5432` (PostgreSQL).
Production публикует только HTTPS-домен через внешний nginx; API и база наружу отдельными портами
не открываются. Полная схема и границы компонентов описаны в
[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

Внешние условия проверки: доступ к MAX и его Bot API/Bridge CDN, публичные DNS и TLS для
`max.fblrkus.ru`, действующий токен бота и две роли MAX для сквозной проверки отметки. Рабочие
секреты передаются отдельно; `.env.example` содержит только имена и безопасные примеры.

## Работа с данными

- **Что хранится:** идентификатор MAX, имя, выбранный язык, согласие и время его принятия, записи на
  события, отметки посещения и баллы. Паспортных, контактных и медицинских данных нет.
- **Согласие (152-ФЗ):** без принятого согласия API разрешает только операции профиля `/api/me` и
  `/api/me/consent`; остальные операции недоступны.
- **Доступ:** студент видит свои данные; организатор видит явку и CSV только по своим событиям;
  администраторы задаются переменной `ADMIN_MAX_USER_IDS`. Каждый запрос подписан `initData` MAX.
- **Тестовые данные:** `python -m campus.seed` (сервис `seed` в Compose) идемпотентно создаёт
  синтетический «Университет N», события и демо-пользователей и печатает приглашение организатора.
  Реальных данных вуза или студентов в репозитории нет; интеграции с ЛК, расписанием и СКУД вуза
  не реализованы и в MVP не имитируются.
- **Логи:** структурированный JSON; токен, `initData`, `qr_seed` и коды отметки маскируются.

## Техническая проверка API

Контракт OpenAPI 3.1 находится в [`docs/openapi.json`](docs/openapi.json), а обязательный сценарий
DATA-API 1.0 — в [`DATA-API.yaml`](DATA-API.yaml). Публично доступны:

```sh
curl https://max.fblrkus.ru/health
curl https://max.fblrkus.ru/openapi.json
```

Официальный валидатор запускается из отдельного checkout репозитория организаторов:

```sh
python3 -m venv /tmp/data-api-validator-venv
/tmp/data-api-validator-venv/bin/pip install -r /path/to/example-data-api/requirements.txt
/tmp/data-api-validator-venv/bin/python /path/to/example-data-api/validate_data_api.py \
  ./DATA-API.yaml \
  --schema /path/to/example-data-api/Example/DATA-API.schema.json \
  --openapi ./docs/openapi.json
```

`DATA-API.yaml` не содержит учётные данные. Проверяющая система должна безопасно подставить свежие
`${studentInitData}` и `${organizerInitData}`; их срок жизни по умолчанию — 3600 секунд. Подготовка
ролей, текущего события и повторного прогона описана в
[`docs/TECHNICAL_CHECK.md`](docs/TECHNICAL_CHECK.md).

## Остановка и повторный запуск

```sh
docker compose down       # остановить, сохранив PostgreSQL volume
docker compose up --build # повторно собрать и запустить
```

Seed идемпотентен: повторный запуск обновляет время синтетических событий и не создаёт их копии.
Для полного сброса локальных демонстрационных данных используйте `docker compose down --volumes`,
после чего снова выполните быстрый старт. Эта команда удаляет локальную базу безвозвратно.

## Известные ограничения

- Продукт использует синтетическую конфигурацию «Университета N» и не подключён к реальному
  расписанию, СКУД или информационной системе вуза.
- Роль организатора выдаётся одноразовым приглашением; общедоступной саморегистрации этой роли нет.
- QR сканируется камерой другого устройства. Для проверки с одного устройства доступен ручной
  шестизначный код, показанный организатору рядом с QR.
- Код ротируется каждые 10 секунд (`CHECKIN_CODE_STEP_SECONDS`). QR, отсканированный камерой,
  проверяется по подписанному MAX времени скана, поэтому сетевая задержка не мешает. Ручной ввод
  проверяется по времени запроса: шесть цифр нужно отправить до смены кода, иначе приложение
  попросит ввести новый. Для ручного ввода в зале шаг можно увеличить переменной окружения.
- Повторная отметка одного студента идемпотентна: API отвечает `already=true` и не начисляет баллы
  повторно.
- Уведомления зависят от доступности MAX Bot API. Бот использует один процесс long polling; активная
  webhook-подписка для того же токена должна быть удалена.
- Кнопка сканера появляется, только если клиент MAX предоставляет камеру (`openCodeReader`); её
  работа в MAX Web не подтверждена. Без камеры отметка выполняется ручным шестизначным кодом,
  остальные экраны одинаковы в мобильной и веб-версии.
