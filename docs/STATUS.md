### Фаза 2 — процессы (вмержено в `main`)
**`campus.api`** — FastAPI поверх домена: все 20 операций §7, включая `GET /api/config` и `GET /health` с проверкой БД. Проверка `initData` на каждом запросе (подпись + TTL `auth_date`), согласие по правилу §7, доменные ошибки строго из закрытого списка, `Date` на каждом ответе и `Retry-After` на 429. `docs/openapi.json` экспортируется из самого приложения, CI падает на устаревшем файле.

**`campus.bot`** — один процесс под advisory-lock: long polling с маркером в `kv`, сценарии `/start` (пусто / `org_<token>` / `ev_<id>`), меню, карточка события с RSVP, ввод кода в чат, воркер ротации QR (upload + `PUT /messages`, одна активная display на организатора+событие) и воркер `outbox` (`FOR UPDATE SKIP LOCKED`, 5 попыток с ростом задержки, все 5 типов). Тексты только из i18n.

**Ревью тремя агентами (fastapi / python / security).** CRITICAL по безопасности не найдено: обхода аутентификации, обхода проверки владельца, SQL-инъекций и утечки токена нет; §5 (HMAC-коды, окна, атомарный rate limit) реализован по контракту. Найденное и **исправленное** в этой же ветке:
- **CRITICAL (бот):** пустой long-poll-ответ приходит без маркера, а цикл всё равно ставил чекпоинт — это стирало маркер, и MAX переотдавал всю очередь. Теперь пустая пачка маркер не трогает.
- **HIGH:** 401 от MAX больше не считается ошибкой доставки (иначе вся очередь уходила в `failed` безвозвратно); бот не стартует без `MAX_BOT_USERNAME` (без него QR не собирался никогда); кодом считается только 6 цифр, а не любой текст (десяток случайных сообщений выжигал лимит §5), и режим ввода перестал быть «липким»; подтверждение отметки и принятие приглашения больше не приходят дважды; списки отправляются одним сообщением (25 событий держали бота 25 секунд); при `LOG_LEVEL=DEBUG` SQLAlchemy больше не печатает параметры запросов с кодами, а маскирование ловит форму `"code": "123456"`.
- **MEDIUM:** `Retry-After` от MAX ограничен сверху, иначе один перегруженный чат останавливал polling и ротацию QR на час; списки событий ограничены 200 строками; тело запроса больше 256 КиБ отклоняется до чтения; 500 пишет в лог метод, шаблон маршрута и трассировку; состояние диалога в `kv` живёт 30 минут (раньше токен приглашения оставался там навсегда); Swagger UI выключен.

**Осталось из ревью (не блокирует, вынесено за Фазу 2):** нет общего rate limit на остальных эндпоинтах (нужен на уровне Caddy); тик `outbox` — одна транзакция на пачку (откат в середине может переотправить уже отправленное); сеть держится внутри открытой транзакции в QR-воркере; `SIGTERM` рвёт пачку без drain; разбор `start`-payload дублирует `domain/deeplinks.py`; 404/405 отвечают формой Starlette, а не конвертом §7 — по контракту это транспортные ответы, решение зафиксировано здесь осознанно.

### Исправление в PR #13
- Seed раньше ставил в `outbox` 12 напоминаний по RSVP и 3 сообщения `step_completed` для синтетических пользователей MAX. Именно три последние строки соответствуют предупреждениям для `outbox_id` 13–15 в логах 19.09. Seed теперь записывает демонстрационные RSVP и ручные шаги без отправки сообщений; повторный запуск отменит старые `pending` и `failed` задания для этих пользователей.
- `update_failed` — отдельная ошибка обработки входящего обновления. Старые логи содержат только `MaxApiError`, поэтому её точную причину установить нельзя. В новых логах будут тип обновления, операция MAX, HTTP-статус и код ошибки без текста ответа и URL загрузки.
- При деплое PR #13 сервис `seed` был запущен повторно; workflow завершился успешно.

### Ошибка кнопки согласия на VPS (PR #14)
- Логи бота на VPS после нажатия «I give consent» показывают `update_failed` для `message_callback`: MAX отвечает `400 proto.payload` на `POST /answers`. Бот отправлял пустое `{}` до обработки callback, поэтому согласие не сохранялось, а маркер polling уходил дальше.
- В PR #14 обработчик выполняет действие без пустого `/answers`; клиент MAX и его fake отклоняют попытку отправить пустой ответ. После доставки PR нужно нажать кнопку снова: ранее пропущенные обновления не воспроизводятся.

### Inline-кнопки и запуск мини-приложения (текущая ветка)
- После PR #14 callback отправлял новое сообщение, оставляя старую клавиатуру. Теперь действие сначала сохраняется, затем непустой `POST /answers` удаляет старые вложения, и новые сообщения с актуальными кнопками появляются внизу чата. При ошибке `/answers` предусмотрено редактирование старого сообщения по `message_id`; ответ пользователю отправляется независимо от ошибки очистки.
- После первого ручного шага онбординга кнопок не было по логике данных: остальные четыре шага требуют отметки на мероприятии. Для каждого такого шага добавлен переход к подходящим будущим мероприятиям и пояснение, что RSVP не равен отметке. Добавлены кнопки возврата в меню для конечных состояний.
- `open_app.web_app` по схеме MAX содержит публичное имя бота; текущий production использует
  `se13836036_1_bot`. Параметр `ev_<id>` открывает карточку события в мини-приложении.
- Публичный `https://max.fblrkus.ru/`, JS/CSS и MAX Bridge CDN отвечают HTTP 200; `GET /api/config` без данных запуска возвращает 401, как ожидается. В присланных логах `web` есть только проверки `GET /` с `127.0.0.1`; они не подтверждают попытку запуска через MAX. Ошибка «failed to open mini app» вероятно связана с отсутствующей привязкой URL в настройках бота; проверить поле может только владелец бота. Владельца попросили через GitHub.

## Открытые вопросы и риски
- **Мини-приложению нужен публичный HTTPS.** У жюри в Docker без домена оно не поднимется. Надо спросить организаторов, кто прописывает URL мини-приложения и засчитывается ли наш хостинг.
- **Бот привязан к ИНН владельца** и не передаётся вузу: для пилота нужен отдельный бот.
- **Репозиторий к сдаче.** Каталог `internal/max_bot_from_inna/` с чужим кодом без подтверждённой лицензии удалён из сдаваемого дерева. Перед окончательной публикацией отдельно решить, нужно ли исключить внутренние исследования (`internal/`, `.claude/notes/`) и очищать историю репозитория.
- **Пилот до 29.10** возможен только на текущих мероприятиях: онбординг первокурсников уже прошёл.
- **Долги из ревью фронта закрыты в PR #5:** экран QR опрашивает событие со счётчиком без списка ФИО; опросы события и явки останавливаются на ошибке; `I18nProvider` обновляет `<html lang>`; сетевая ошибка отметки и ручной повтор покрыты тестом.

## Статус долгов в контракте
- **Противоречие по `INIT_DATA_TTL_SECONDS` закрыто:** §7, §10, код, unit-тест и `.env.example` теперь задают единый default 3600 секунд. Часовое окно сокращает время повторного использования утёкшего `initData`.
- **`origin/feat/api` устарела и не требует слияния:** `not_admin` уже есть в `main` в доменной ошибке, закрытом словаре кодов и тестах; эквивалентное изменение TTL на 3600 секунд перенесено напрямую. Удаление remote-ветки остаётся отдельным действием владельца репозитория.
- **Четыре кода из закрытого списка §7 недостижимы по HTTP:** `ambiguous_code` требует запроса без `event_id` (в §7 он обязателен), а `invite_invalid` / `invite_used` / `invite_expired` возникают только на пути бота. Пометить их в §7 как коды бота.

В реализации уже описаны формат `POST /uploads` и точный алгоритм `initData`, но контракт пока отсылает к документации MAX без этих подробностей. После живых проверок перенести подтверждённые детали в `docs/ARCHITECTURE.md`. TTL `initData` (по умолчанию 3600 с), код `not_admin` и осознанный выбор long polling зафиксированы в `main`.
